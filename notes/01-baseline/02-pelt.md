# PELT 负载跟踪（baseline）

> **源码**：[pelt.c](../../kernel/kernel/sched/pelt.c)、[pelt.h](../../kernel/kernel/sched/pelt.h)、[sched-pelt.h](../../kernel/kernel/sched/sched-pelt.h)、[fair.c](../../kernel/kernel/sched/fair.c)
> **内核版本**：5.15.211 (Qualcomm, sm8550/lineage-21)
> **最后核对**：2026-09-17

PELT（Per-Entity Load Tracking）是原生调度器的负载跟踪机制，
**也是 WALT 所旁路（而非删除）的那套机制**。
理解 PELT 是指出 WALT 「改了什么、为什么改」的前提。

> **两条重要的定位修正**（影响阅读源码的位置）：
> 1. `struct sched_avg` / `struct util_est` 定义在
>    [include/linux/sched.h](../../kernel/include/linux/sched.h#L486)，
>    **不在** `kernel/sched/sched.h`。后者只是把 `struct sched_avg avg`
>    嵌进 `struct cfs_rq`（[sched.h:575](../../kernel/kernel/sched/sched.h#L575)）。
> 2. `update_load_avg()` / `update_cfs_rq_load_avg()` **不在 pelt.h**，
>    它们是 [fair.c](../../kernel/kernel/sched/fair.c) 里的 `static inline`。
>    `pelt.h` 只声明 `__update_*` 系列。

---

## 1. 一句话模型

把「一个任务可运行」这个事实按**几何级数衰减**加权，
得到一个连续的、永远变化的值。半衰期 **32 ms**。

```
util_avg(t) = util_avg(t-1) × y + (本次是否在跑) × (1 - y)
其中 y = 2^(-1/32) ≈ 0.9786，即 y^32 = 0.5
```

与 WALT 的「窗口 + 峰值」相比，PELT 是「**连续 + 平均**」。
这个差异是两者一切行为分歧的根源。

## 2. 几何衰减的实现

### 2.1 常量

[sched-pelt.h](../../kernel/kernel/sched/sched-pelt.h)：

```c
/* Generated by Documentation/scheduler/sched-pelt; do not modify. */
static const u32 runnable_avg_yN_inv[] = {
        0xffffffff, 0xfa83b2da, 0xf5257d14, ... , 0x82cd8698,
};

#define LOAD_AVG_PERIOD 32
#define LOAD_AVG_MAX   47742
```

| 常量 | 值 | 含义 |
|---|---|---|
| `LOAD_AVG_PERIOD` | 32 | 半衰期对应的周期数 |
| `LOAD_AVG_MAX` | 47742 | `1024 × Σyⁿ`，无穷级数和的定点表示 |
| `runnable_avg_yN_inv[n]` | `⌊yⁿ × 2³²⌋` | `yⁿ` 的 Q32 定点表 |

> **这个文件是自动生成的**（首行注释说明），不要手改。
> 生成器在 `Documentation/scheduler/sched-pelt`。

推导：`LOAD_AVG_MAX = 1024 × Σ_{n=0}^{∞} yⁿ = 1024 / (1 - y) ≈ 47742`。
所以 `LOAD_AVG_MAX - 1024 = 46718 = 1024 × Σ_{n=1}^{∞} yⁿ`。

### 2.2 `decay_load()`

[pelt.c:35](../../kernel/kernel/sched/pelt.c#L35)。计算 `val × yⁿ`，**O(1)**：

```c
if (n > LOAD_AVG_PERIOD * 63)
        return 0;                                   /* y^2016 ≈ 2^-63，下溢 */

val >>= local_n / LOAD_AVG_PERIOD;                  /* 利用 y^32 = 1/2 */
local_n %= LOAD_AVG_PERIOD;

val = mul_u64_u32_shr(val, runnable_avg_yN_inv[local_n], 32);
```

**核心技巧**：因为 `y³² = 0.5`，`yⁿ` 可以拆成
「整数个半衰期（右移）」×「余数的查表乘法」。
这正是 `LOAD_AVG_PERIOD = 32` 这个特定值的意义。

### 2.3 `__accumulate_pelt_segments()`

[pelt.c:61](../../kernel/kernel/sched/pelt.c#L61)。三段式：

```
   ├──── d1 ────┼────── d2 ──────┼── d3 ──┤
   上一个不完整周期   若干完整周期     当前不完整周期
```

- `d1 = 1024 - period_contrib`（上一个周期剩下的部分）
- `c1 = d1 × y^periods`
- `c2 = 1024 × Σ_{n=1}^{periods-1} yⁿ = LOAD_AVG_MAX - decay_load(LOAD_AVG_MAX, periods) - 1024`
- `c3 = d3`（当前周期，未衰减）

返回 `c1 + c2 + c3`。

**这个函数的取值上限是 `LOAD_AVG_MAX`**——这就是那个常数的物理含义：
一个「永远在跑」的任务稳态下累计的贡献。

## 3. `struct sched_avg`

[include/linux/sched.h:486-496](../../kernel/include/linux/sched.h#L486-L496)：

```c
struct sched_avg {
        u64                     last_update_time;
        u64                     load_sum;
        u64                     runnable_sum;
        u32                     util_sum;
        u32                     period_contrib;
        unsigned long           load_avg;
        unsigned long           runnable_avg;
        unsigned long           util_avg;
        struct util_est         util_est;
} ____cacheline_aligned;
```

| 字段 | 类型 | 单位 / 含义 |
|---|---|---|
| `last_update_time` | `u64` | **PELT 时钟**（`rq_clock_pelt()`）的 ns 值，**不是**原始 ns |
| `load_sum` | `u64` | 加权可运行时间，单位是权重（`scale_load_down(weight)`）|
| `runnable_sum` | `u64` | **不加权**的可运行时间，`<< 10` 定点 |
| `util_sum` | `u32` | **正在跑**的时间，`<< 10` 定点 |
| `period_contrib` | `u32` | 当前周期内的位置，`[0, 1023]` |
| `load_avg` | `unsigned long` | 权重尺度，**未归一化到 1024** |
| `runnable_avg` | `unsigned long` | `[0, 1024]`，「可运行占比」 |
| `util_avg` | `unsigned long` | `[0, 1024]`，「实际运行占比」 |
| `util_est` | `struct util_est` | 见 §5 |

### 3.1 三个 `_avg` 的语义区分 [重要]

[include/linux/sched.h:441-485](../../kernel/include/linux/sched.h#L441-L485)
的注释给出了形式化定义：

```
load_avg     = runnable% × scale_load_down(load)
runnable_avg = runnable% × SCHED_CAPACITY_SCALE
util_avg     = running%  × SCHED_CAPACITY_SCALE
```

- **runnable**：任务在 runqueue 上（含等待）——「想要 CPU」
- **running**：任务真的在 CPU 上——「得到 CPU」

> 【反直觉】`load_avg` 与另两者的**尺度不同**：它是权重乘出来的，
> 一个 nice 0 的任务 load 为 1024，但一个 nice -20 的任务 load 是 88761。
> 所以 **`load_avg` 不能直接和 1024 比较**。做容量判断要用 `util_avg`。

### 3.2 `util_sum` 为什么是 `u32` 就够

`util_sum` 最大为 `LOAD_AVG_MAX << 10 = 47742 × 1024 = 48,887,808`，
而 `u32` 上限约 42.9 亿——**两个数量级的余量**。
`load_sum` 因为要乘权重，必须用 `u64`。

## 4. 更新流程

### 4.1 `___update_load_sum()`

[pelt.c:183](../../kernel/kernel/sched/pelt.c#L183)：

```c
delta = now - sa->last_update_time;
if ((s64)delta < 0) {                       /* 时钟回退（TSC 切换）*/
        sa->last_update_time = now;
        return 0;
}
delta >>= 10;                               /* ns → 1024ns 单位 */
if (!delta)
        return 0;                           /* 不足 1024ns，直接返回 */

sa->last_update_time += delta << 10;        /* 对齐到 1024ns 边界 */

if (!load)
        runnable = running = 0;             /* running ⊆ runnable */

if (!accumulate_sum(delta, sa, load, runnable, running))
        return 0;
return 1;                                   /* 返回 1 = 跨过了周期边界 */
```

> **「1024ns 为单位」** 注释说明了理由：接近 1μs 且移位计算快。
> 副作用是 **`update_load_avg` 的精度是 1μs**——
> 比它短的时间差完全不记，但会累积到下次。

### 4.2 `accumulate_sum()`

[pelt.c:106](../../kernel/kernel/sched/pelt.c#L106)。**这是整个 PELT 的核心。**

```c
u32 contrib = (u32)delta;                   /* 默认：p == 0 分支 */
u64 periods;

delta += sa->period_contrib;
periods = delta / 1024;                     /* 一个周期 = 1024 × 1024ns ≈ 1.05ms */

if (periods) {                              /* ← 分支 B：跨了周期边界 */
        sa->load_sum     = decay_load(sa->load_sum, periods);
        sa->runnable_sum = decay_load(sa->runnable_sum, periods);
        sa->util_sum     = decay_load((u64)(sa->util_sum), periods);

        delta %= 1024;
        if (load)
                contrib = __accumulate_pelt_segments(periods,
                                        1024 - sa->period_contrib, delta);
}
sa->period_contrib = delta;

if (load)
        sa->load_sum += load * contrib;
if (runnable)
        sa->runnable_sum += runnable * contrib << SCHED_CAPACITY_SHIFT;
if (running)
        sa->util_sum += contrib << SCHED_CAPACITY_SHIFT;

return periods;
```

**时间单位换算表**：

| 名称 | 长度 |
|---|---|
| 测量单位 | 1024 ns |
| 一个周期 | 1024 个测量单位 = 1024 × 1024ns ≈ **1.05 ms** |
| 半衰期 | `LOAD_AVG_PERIOD` = 32 个周期 ≈ **32.8 ms** |
| 时间常数 | `LOAD_AVG_MAX/1024` ≈ 46.6 个周期 ≈ **48.9 ms** |

> **三层不同量级的时间单位容易搞混**：
> 1024ns（测量单位）→ 1.05ms（周期）→ 32.8ms（半衰期）。
> 注释里同时出现 "1024"（测量单位数）和 "1024us"（周期长度），
> 读代码时要看清是哪个。

### 4.3 `___update_load_avg()`

[pelt.c:260](../../kernel/kernel/sched/pelt.c#L260)：

```c
u32 divider = get_pelt_divider(sa);         /* = PELT_MIN_DIVIDER + period_contrib */

sa->load_avg     = div_u64(load * sa->load_sum, divider);
sa->runnable_avg = div_u64(sa->runnable_sum, divider);
WRITE_ONCE(sa->util_avg, sa->util_sum / divider);
```

除数（[pelt.h:40-45](../../kernel/kernel/sched/pelt.h#L40-L45)）：

```c
#define PELT_MIN_DIVIDER (LOAD_AVG_MAX - 1024)      /* = 46718 */

static inline u32 get_pelt_divider(struct sched_avg *avg)
{
        return PELT_MIN_DIVIDER + avg->period_contrib;
}
```

> **为什么除数不是 `LOAD_AVG_MAX` 而是 `LOAD_AVG_MAX - 1024 + period_contrib`？**
> 源码注释 [pelt.c:236-259](../../kernel/kernel/sched/pelt.c#L236-L259) 解释了：
> 能达到的 `_sum` 最大值取决于「当前处在周期内的什么位置」。
> 因为 `LOAD_AVG_MAX × y = LOAD_AVG_MAX - 1024`，
> 所以「一个周期前」的值就是 `LOAD_AVG_MAX - 1024`。
> 用这个动态除数，`_avg` 在稳态下才恰好收敛到 1024（满负荷）。

### 4.4 两条更新路径的分工

```
___update_load_sum(now, sa, load, runnable, running)   → 累加 *_sum
___update_load_avg(sa, load)                           → 算出 *_avg
```

**必须成对调用**。中间的 `accumulate_sum()` 返回 0 时表示没跨周期，
`___update_load_avg()` 仍要调用（`_sum` 变了，`_avg` 就要重算）。

## 5. `util_est`：利用历史峰值

PELT 是纯平均，对「刚醒来的重任务」估计偏低。`util_est` 是对此的补丁。

### 5.1 结构

[include/linux/sched.h:434-439](../../kernel/include/linux/sched.h#L434-L439)：

```c
struct util_est {
        unsigned int            enqueued;
        unsigned int            ewma;
#define UTIL_EST_WEIGHT_SHIFT   2
#define UTIL_AVG_UNCHANGED      0x80000000
} __attribute__((__aligned__(sizeof(u64))));
```

| 字段 | 含义 |
|---|---|
| `enqueued` | 任务上次 dequeue 时的 `util_avg`；对 cfs_rq 是其所有可运行任务之和 |
| `ewma` | 历史 util 的指数加权平均（`w = 1/4`）|

> **`UTIL_AVG_UNCHANGED` 复用最高位**：因为一个任务的
> `util_est.enqueued ≤ 1024`，最高位永远为 0，可以安全地拿来当
> 「自入队以来 util_avg 是否变过」的标志位。

### 5.2 `_task_util_est()`

[fair.c:3966-3971](../../kernel/kernel/sched/fair.c#L3966-L3971)：

```c
return max(ue.ewma, (ue.enqueued & ~UTIL_AVG_UNCHANGED));
```

取两个估计的**较大值**，并**掩掉标志位**。

### 5.3 `util_est_update()`

[fair.c:4025](../../kernel/kernel/sched/fair.c#L4025)。几个重要细节：

**(a) 迁移时跳过**

```c
if (!task_sleep)
        return;                     /* 未完成一次完整激活，样本无效 */
```

**(b) 只在「已变化」时更新**

```c
if (unlikely(ue.enqueued & UTIL_AVG_UNCHANGED))
        return;
```

该标志在入队时置位（[:4110](../../kernel/kernel/sched/fair.c#L4110)），
在 `cfs_se_util_change()`（[pelt.h:47](../../kernel/kernel/sched/pelt.h#L47)）
检测到 `util_avg` 变化时清除。

**(c) `UTIL_EST_FASTUP`：EWMA 只平滑下降** [反直觉]

```c
if (ewma < enqueued)
        ewma = enqueued;            /* util 上升时直接跳到新值 */
```

即：**上升立即跟上，下降才做平滑**。这是「宁可高估」哲学的又一处体现。

**(d) 两个跳过条件**

- 差值在 `UTIL_EST_MARGIN`（= 10 = `1024/100`）以内 → 跳过
- `task_util(p) > capacity_orig_of(cpu)` → 跳过（避免高估）

**(e) EWMA 公式**

```c
ewma_new = (ewma<<2 + (enqueued - ewma)) >> 2
         = 0.25 × enqueued + 0.75 × ewma
```

### 5.4 消费

`sched.h:3118` 的 `cpu_util_cfs()`：

```c
max(rq->cfs.avg.util_avg, rq->cfs.avg.util_est.enqueued)
```

**`UTIL_EST` 开启时，util 是 `util_avg` 与 `util_est.enqueued` 的较大者。**

### 6.2 `update_cfs_rq_load_avg()`

[fair.c:3702](../../kernel/kernel/sched/fair.c#L3702)。**先清 `removed` 链表**

> 等下次同步时统一用 `_avg × divider` 反推 `_sum` 再减。
> 见 [sched.h:579-585](../../kernel/kernel/sched/sched.h#L579-L585)。

## 7. `util_avg` 的消费链

```
sched_avg.util_avg
   └─ cpu_util_cfs(rq)        sched.h:3108
        └─ effective_cpu_util()  core.c:7320
             ├─ sugov_get_util()   cpufreq_schedutil.c:201   → 调频
             └─ sched_cpu_util()   core.c:7411                → EAS 能耗
```

> **这条链没有被 WALT 短路。** `effective_cpu_util()` 里确实有一个
> vendor hook 短路点（[core.c:7328-7330](../../kernel/kernel/sched/core.c#L7328-L7330)），
> 但在**本树中它从未被注册**，因此永远不会触发，函数体完整执行。
> WALT 是**绕开**这条链，而不是改写它——见
> [schedutil.md §3.2](03-schedutil.md#32-第-1-步一个未生效的-vendor-hook-短路点-关键) 与
> [02-cpufreq-diff.md §2.1](../03-comparison/02-cpufreq-diff.md)。

**`util_avg` 并未变成死代码**：`cpu_util()` [fair.c:6761](../../kernel/kernel/sched/fair.c#L6761)
在负载均衡里仍被使用，而 load balance 的 WALT 替换是**部分的**
（见 [../02-walt/05-load-balance.md](../02-walt/05-load-balance.md)）。

`update_rq_clock_pelt()` 是 PELT 的「频率不变性」来源——
它让 `util_avg` 在概念上等价于「满频下的占用率」。

> **这正是 WALT 的 `scale_exec_time()` 做同一件事的地方**
> （见 [window-model.md §8](../02-walt/01-window-model.md#8-频率归一化scale_exec_time)）。
> 两者都想解决「CPU 快慢不同，时间不可直接比较」的问题，
> 但 WALT 用**显式的频率缩放**，PELT 用**缩放时钟**。

## 9. PELT 与 WALT 的对照（速览）

详细对照见 [../03-comparison/base-vs-walt.md](../03-comparison/01-base-vs-walt.md)。

| | PELT | WALT |
|---|---|---|
| 抽象 | 连续指数衰减 | 固定长度窗口 |
| 信号 | 平均值（`util_avg`）| 窗口内累计（`sum`）→ 历史**峰值**（`demand`）|
| 时间常数 | 半衰期 32.8ms | 5 窗口（默认 ~100ms）|
| 上升响应 | 渐进（EWMA 有 FASTUP 补丁）| 下一窗口即达峰值 |
| 下降响应 | 渐近（永不归零）| 空窗口直接丢弃（**会归零**）|
| 每任务成本 | `struct sched_avg`（~72B）| `struct walt_task_struct`（51 字段）|
| 历史长度 | 隐含在 `_sum` 中 | 显式 5 项环（`sum_history`）|
| 是否被移除 | — | **没有**，仍并行维护 |

> 【反直觉】**WALT 并没有删除 PELT。** `struct sched_avg` 仍在每次
> `enqueue_entity` / `dequeue_entity` 时更新，`util_avg` 仍被
> load balance 使用。WALT 只是让**调频**不再读它。
> 这解释了为什么 `update_load_avg()` 的调用点一个都没少。
